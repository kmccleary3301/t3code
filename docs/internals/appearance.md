# Appearance architecture

This document records the appearance model and its boundaries for maintainers. It turns the G0 foundation decisions into durable architecture facts. It is not a feature checklist.

## Scope and ownership

Appearance customization covers T3-owned renderer content in web, desktop, and mobile clients. A normalized profile is the input to each renderer. Storage, package parsing, preference resolution, and recovery stay outside UI components.

The distinction matters. An excluded OS dialog is not an implementation gap. A missing mobile safe-mode route, browser package store, or desktop stylesheet watcher is an implementation gap.

Raw CSS can style internal DOM details, but it is version-sensitive. Only documented supported tokens and stable selectors carry compatibility guarantees.
The web hook vocabulary and compatibility policy are normative in [`appearance-selectors.md`](./appearance-selectors.md).

## Fixed module and seam decision

The stable client-facing runtime has three methods:

```ts
interface AppearanceRuntime {
  getSnapshot(): AppearanceSnapshot;
  subscribe(listener: () => void): () => void;
  execute(command: AppearanceCommand): Promise<AppearanceCommandResult>;
}
```

`AppearanceCommand` is a tagged union for install, uninstall, activate, import, export, reorder, enable, disable, reload, theme-draft save, appearance-mode changes, font and accessibility preference overrides, preview, clear-preview, safe-mode entry, and reset. `AppearanceSnapshot` is immutable resolved state. Renderers do not parse files, read storage, call IPC, or inject stylesheets.

The ownership and seam are fixed:

There is one active theme package and an ordered set of independently enabled local snippets. No second runtime or compatibility re-export remains after callers migrate.

## Storage, ownership, and migration

- Active theme identity, light/dark choices, snippet state and order, custom appearance data, previews, and diagnostics are client-local. A remote connection does not change a browser's local appearance authority.
- Browser package text and assets are stored in IndexedDB. File imports are copied into browser storage. A bounded synchronous boot snapshot is used only to avoid a prepaint flash.
- Desktop package files and snippets live in the desktop user-data area through `DesktopAppearanceStorage`, not in the server's shared runtime database. Writes are atomic; watcher events are debounced and deduplicated.
- Mobile stores the portable manifest subset in the existing device-local appearance store. Package CSS and snippets never execute on mobile.
- The server can publish bounded environment palettes and a default-theme reference. It cannot send raw CSS for automatic execution. Export/import is the first synchronization mechanism. Cloud sync is a separate approved plan.
- Existing version 1 theme files and appearance preferences are migration inputs. Decode and normalize them before removing direct v1 stores. Migrate every caller, verify the new storage, then remove obsolete direct reads, writes, aliases, and re-exports. Do not delete a source that failed migration; quarantine it and preserve export/recovery access.

## Resolution precedence

Resolve one profile in this order:

1. Standard T3 defaults.
2. Selected light or dark theme manifest values.
3. Active theme package CSS.
4. Explicit client font, appearance, and accessibility preference variables.
5. Enabled advanced snippets in stored order.
6. Transient editor preview in isolated-theme or with-snippets mode.
7. Pre-injection safe-mode bypass and ordinary accessibility rules.

The CSS layer order mirrors this contract: `t3.reset`, `t3.base`, `t3.components`, `t3.theme`, `t3.preferences`, `t3.snippets`, and `t3.accessibility`. Manifest values and package CSS provide defaults. Explicit client preferences reassert supported variables after package CSS. Advanced snippets intentionally remain a full-control escape hatch and can override ordinary preferences. Safe mode does not compete in the cascade. It skips custom CSS, assets, and boot-cache use before the renderer exists.

Trust is about origin and capability, not whether a file happens to parse. `community-reviewed` is reserved for a later distribution system and is not implied by local installation.

## Fixed package bounds

These initial limits are part of the contract. A reduction needs a recorded decision. An increase, new asset type, broader CSS or URL grammar, or new trust class requires human approval, independent security review, an updated threat model, and refreshed adversarial evidence.

- Manifest: at most 256 KiB.
- Each CSS file: at most 1 MiB.
- Extracted package: at most 20 MiB.
- Files: no more than 256.
- Path depth: at most eight segments.
- Reject symlinks, hard links, absolute paths, `..`, executable files, HTML, and JavaScript.
- Allow only WOFF2, PNG, JPEG, WebP, and AVIF assets initially.
- SVG is disabled until external references, scripts, and parser behavior receive a separate security review.
- Resolve local asset URLs through a path-contained app protocol or generated blob URL, never arbitrary filesystem URLs.

## Version 2 author contract

The portable contract is exported as `@t3tools/shared/appearance`. Every input enters through `normalizeAppearance`. Renderers and runtime adapters consume `NormalizedAppearanceProfile`; they do not inspect manifest JSON or version 1 theme objects.

Version 2 manifests are strict. Unknown fields at any depth are errors. A manifest declares:

- `schema: "t3.appearance/v2"` and `version: 2`.
- Stable package metadata: strict id, bounded nonblank name, and SemVer version without a build suffix. Versions are at most 128 characters; core and numeric prerelease components are at most nine digits so every supported client compares them exactly. Author, license, description, and homepage are optional.
- Compatibility: supported platforms, required capabilities, and optional ordered minimum and maximum app versions.
- Requested capabilities, an explicit `light` and `dark` fallback policy, a default variant id, one to 32 uniquely identified variants, and no more than 256 assets.
- Each variant's light or dark appearance and all 57 color roles. Typography, metrics, motion, terminal, syntax, and diff sections are optional in author input and complete after normalization.
- Optional `styles.web` and `styles.desktop` entries. Each is a relative path of at most eight segments, a lowercase SHA-256 digest, and a byte size no greater than 1 MiB. The matching `shared-css` or `desktop-css` capability and entrypoint must be declared together.
- Optional presentation metadata preserves reviewed sidebar artwork, managed-theme identity, and collection grouping across version 1 migration.

Typography has semantic `interface`, `composer`, `code`, `terminal`, `markdown`, `label`, and `heading` roles. Every role contains ordered fallback families, pixel size, weight, unitless line height, em letter spacing, ligature policy, and four-character variable-font axes.

Metrics define density, spacing and radius scales, border and shadow scales, bounded sizing ranges, content width and gutters, panel gaps, and sidebar position. Sizing ranges must satisfy `minimumPx <= preferredPx <= maximumPx`. Motion defines ordered durations, easing values, semantic color/surface/layout/opacity transitions, animation enablement, and reduced-motion policy. Durations must increase from `instant` through `slow`.

Terminal data is renderer-neutral: foreground, background, cursor, selection, scrollbar, and the complete 16-color ANSI palette. Syntax rules map one or more scopes to foreground, optional background, and font styles. Diff roles cover base, additions, deletions, modifications, gutters, line numbers, hunks, selection, comments, and headers. Web, desktop, and mobile adapters translate these values into their renderer-specific APIs.

Assets are declarations, not bytes embedded in the manifest. Paths must be relative, contain no `..`, and have at most eight segments. Every asset declares a lowercase SHA-256 digest, byte size, MIME type, and target platforms. Initial image types are PNG, JPEG, WebP, and AVIF. Fonts are WOFF2 and must declare a family. SVG, HTML, JavaScript, executable files, absolute paths, links, and undeclared MIME types are rejected. The package loader must also enforce the aggregate package bounds above before activation.

Trust is supplied by the installation boundary, never self-asserted by a manifest. The fixed classes are `builtin`, `local-package`, `local-snippet`, `environment-palette`, and reserved `community-reviewed`. Theme manifests cannot use the snippet class. Environment palettes cannot receive CSS or snippet grants. A local package requests capabilities in its manifest; normalization computes effective capabilities from those requests and explicit installer grants. CSS entrypoints fail normalization when the corresponding grant is absent.

Compatibility failures, reversed version bounds, unsupported platforms or capabilities, malformed version 1 themes, future versions, duplicate identities, invalid fallback or stylesheet declarations, and missing defaults return typed diagnostics. A failure never returns a partial profile.

Version 1 stored `ThemeDefinition` values and exported `version: 1` color themes normalize into version 2 profiles. Exported files may contain partial color and variant overrides; omitted roles are filled from the same T3 Chat light or dark defaults used by the version 1 importer. Files without an embedded package id require a strict stable `sourceId` from the importing boundary. Legacy collection ids retain the existing 128-character alphanumeric, dot, colon, and hyphen grammar. The generated version 2 candidate is decoded again before it can become a profile. Migration preserves every resolved color role byte plus collection and managed presentation metadata from exports, sidebar-artwork metadata from stored definitions, and records source and target versions. Built-in light and dark palettes use the same path and are parity-tested.

Canonical serialization recursively sorts object keys by Unicode code unit, preserves array order, normalizes negative zero, and rejects cycles, non-finite numbers, non-plain objects, and non-JSON values. `appearanceSha256` uses this serialization and SHA-256 from the shared portable implementation, so browser, desktop, and mobile produce the same lowercase digest without locale-dependent ordering.

Schema additions within version 2 must remain optional at the author boundary and normalize to deterministic defaults. A required-field change, changed default, removed role, widened executable capability, new asset type, or changed canonical form requires a new manifest version, migration, fixtures, security review where applicable, and updated compatibility documentation.

## Current implementation and evidence status

The strict version 2 schema, version 1 migration, normalized built-ins, canonical
hashing, platform-neutral runtime/controller, browser and desktop storage,
package parsing, bounded assets, CSS compiler, ordered snippets, diagnostics,
preview, quarantine, and safe/reset startup paths are implemented in the
owners listed above. Web renderer adapters consume normalized terminal, syntax,
diff, auth, preview, typography, metric, motion, artwork, and selector
contracts. Desktop maps resolved mode and native-safe sRGB colors into the
window background and supported titlebar chrome. Mobile stores and compiles the

Focused schema, runtime, storage, compiler, adapter, recovery, selector, desktop
window/protocol, and mobile adapter tests provide code-level conformance. They
do not replace release evidence. The required packaged desktop matrix on macOS,
Windows, and Linux; hosted/local/offline/multi-tab browser scenarios; iOS and
Android release-device recovery scenes; destructive-style recovery interaction;
screenshots; accessibility snapshots; and startup/switch performance

approval.

These evidence limits do not change the platform-owned exclusions below.

## Native platform limits

Appearance controls stop at the T3-owned shell boundary. Electron can set the
native light/dark source and the BrowserWindow background/titlebar overlay, but
the operating system owns menu bars, context menus created by the OS, file and
folder pickers, permission prompts, share sheets, and window controls. Their
colors, typography, spacing, and contrast may follow system settings rather
than the active T3 profile.

The three desktop targets also differ in what Electron can draw: macOS keeps
native traffic lights in the titlebar, while Windows and Linux use an overlay
with T3-provided symbol colors. Window-manager decorations and compositor
behavior remain outside the app's control, so a profile must provide a safe
background and foreground fallback instead of assuming identical native chrome
across platforms.
